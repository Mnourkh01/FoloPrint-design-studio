# v1.4 — DPI / Low-Resolution Warnings

Status: **SHIPPED** on `feature/v1.4-dpi-warnings` (2026-06-06), created from `staging`
at `7090f5a` (merge of PR #2, `feature/v1.3-design-library`). All suites green; see
"Implementation results" at the end. Sections below are the approved plan, annotated
where the implementation deviated.

## 1. Goal

Warn the user when uploaded artwork may print blurry because its source pixel size is
too low for the physical size it will occupy on the product. Image objects only (no
text objects exist yet). The warning is advisory everywhere: nothing blocks save or
render. The server stays the authority for the warning data returned by the API; the
editor computes the same math locally for live UX.

## 2. The DPI formula

### Inputs

| Input | Source | Today |
|---|---|---|
| Asset pixel size | `UploadedAsset.width/height` (set by sharp on every upload; nullable only for hypothetical legacy rows) | exists |
| Placed object size | `DesignObject.width/height`, template canvas px | exists |
| Print area canvas rect | `PrintArea.x/y/width/height`, canvas px | exists |
| Print area physical size | **new**: `PrintArea.widthInches/heightInches` | missing |

### Formula

Canvas pixels are uniform (square), so one px-per-inch scale per axis converts canvas
space to physical space:

```
pxPerInchX = printArea.width  / printArea.widthInches
pxPerInchY = printArea.height / printArea.heightInches

physicalWidthIn  = object.width  / pxPerInchX
physicalHeightIn = object.height / pxPerInchY

dpiX = asset.width  / physicalWidthIn   =  asset.width  * pxPerInchX / object.width
dpiY = asset.height / physicalHeightIn  =  asset.height * pxPerInchY / object.height

effectiveDpi = min(dpiX, dpiY)
```

- `min` because the worse axis governs perceived quality (the contract allows
  non-uniform width/height even though the editor currently scales uniformly).
- **Rotation is irrelevant**: rotating a rigid rectangle does not change its scale, so
  the formula deliberately ignores `rotation`.
- Result is `null` ("unknown") when asset dims are missing or any input is non-finite
  or non-positive. Unknown never warns (no false positives from bad metadata).

### Fallback when physical size is not configured

`widthInches`/`heightInches` are nullable. The shared helper resolves them:

- `widthInches` null → assume `ASSUMED_PRINT_AREA_WIDTH_INCHES = 12` (standard DTG
  platen width).
- `heightInches` null → derive from the resolved width preserving the canvas rect
  aspect: `heightInches = widthInches * area.height / area.width` (uniform ppi).

This satisfies "physical size or configurable assumed size": explicit per-area inches
when seeded, a single documented constant otherwise.

### Warning levels and thresholds

```
effectiveDpi >= 150          → 'ok'
100 <= effectiveDpi < 150    → 'warning'   "may look soft up close"
effectiveDpi < 100           → 'poor'      "will likely print blurry"
unknown inputs               → no level, no warning
```

Rationale: 300 DPI is the print ideal, 150 is the commonly accepted DTG floor at
normal viewing distance, below 100 pixelation is visible. Constants
(`DPI_OK_THRESHOLD = 150`, `DPI_POOR_THRESHOLD = 100`) live in shared next to the
math so both sides agree exactly; boundary values land on the better level
(exactly 150 → ok, exactly 100 → warning).

### Worked examples (seeded front area, 260 canvas px / 12 in → ppi ≈ 21.67)

| Asset px | Placed canvas px | Physical | effectiveDpi | Level |
|---|---|---|---|---|
| 2000 × 2000 | 182 × 182 (default 70% drop) | 8.4 in | ~238 | ok |
| 1000 × 1000 | 182 × 182 | 8.4 in | ~119 | warning |
| 400 × 400 | 182 × 182 | 8.4 in | ~48 | poor |
| 64 × 64 | 182 × 182 | 8.4 in | ~7.6 | poor |

## 3. Where physical print dimensions live

**Decision: nullable `widthInches`/`heightInches` columns on `PrintArea`.**

```prisma
model PrintArea {
  // ...existing fields...
  /// Physical width of the printable area in inches; null = assume 12in DTG platen.
  widthInches   Float?
  /// Physical height in inches; null = derive from widthInches keeping canvas aspect.
  heightInches  Float?
}
```

- Matches how print specs are stated in the real world ("12 × 16 in front print").
- Additive nullable migration: trivially reversible, no backfill needed, existing
  rows keep working through the fallback.
- Per-axis ppi tolerates a physical aspect that does not exactly match the canvas
  rect aspect (the min() keeps the result conservative).
- Future per-product/per-variant print specs can override these at a higher level
  later; the shared math only takes resolved ppi values, so the source can move
  without touching the formula.

Rejected alternative: a single `dpiScale` (px per inch) column. Harder to reason
about when authoring templates, loses the width/height pair that real spec sheets
use, and cannot express per-axis mismatch.

Seed values (aspect-consistent with the canvas rects):

- front 260 × 340 px → `widthInches: 12, heightInches: 15.7`
- back 260 × 380 px → `widthInches: 12, heightInches: 17.5`

## 4. Shared package additions (`packages/shared/src/quality.ts`, new file)

Pure, dependency-free, used by both web (live UX) and api (authority):

```ts
export type PrintQualityLevel = 'ok' | 'warning' | 'poor';

export const DPI_OK_THRESHOLD = 150;
export const DPI_POOR_THRESHOLD = 100;
export const ASSUMED_PRINT_AREA_WIDTH_INCHES = 12;

/** Print area rect plus optional physical size. */
export interface PhysicalPrintArea extends Rect {
  widthInches?: number | null;
  heightInches?: number | null;
}

/** Canvas px per physical inch, per axis, applying the documented fallbacks. */
export function printAreaPpi(area: PhysicalPrintArea): { x: number; y: number };

export interface ObjectQuality {
  dpiX: number;
  dpiY: number;
  effectiveDpi: number;
  level: PrintQualityLevel;
}

/** null when inputs are unusable (missing/non-finite/non-positive). */
export function evaluateObjectQuality(
  asset: { width: number | null; height: number | null },
  object: { width: number; height: number },
  ppi: { x: number; y: number },
): ObjectQuality | null;

export function qualityLevelOf(dpi: number): PrintQualityLevel;

export interface ObjectQualityWarning {
  printAreaKey: string;
  objectIndex: number;
  assetId: string;
  /** Rounded to integer for display and payload stability. */
  effectiveDpi: number;
  level: 'warning' | 'poor';
}

/** Walks a v2 document's placements; returns warnings only (level ok and unknown are silent). */
export function collectQualityWarnings(
  placements: Pick<DesignPlacement, 'printAreaKey' | 'objects'>[],
  areas: PhysicalPrintArea & { key: string }[],
  assetDimsById: Map<string, { width: number | null; height: number | null }>,
): ObjectQualityWarning[];
```

`index.ts` re-exports everything. `validateDesignPlacements` is untouched: quality is
a parallel advisory channel, never a validation error.

## 5. API changes

### DTO shapes (`packages/shared/src/types.ts`)

```ts
export interface PrintAreaDto {
  // ...existing...
  /** Physical printable size in inches; null = client applies the shared fallback. */
  widthInches: number | null;
  heightInches: number | null;
}

/** Wire shape of ObjectQualityWarning (identical fields). */
export interface ObjectQualityWarningDto {
  printAreaKey: string;
  objectIndex: number;
  assetId: string;
  effectiveDpi: number;
  level: 'warning' | 'poor';
}

export interface DesignProjectDto {
  // ...existing...
  /** Advisory only; empty when everything is ok or unknown. Computed at read time. */
  qualityWarnings: ObjectQualityWarningDto[];
}

export interface DesignListItemDto {
  // ...existing...
  /** Worst level across evaluable objects; null when nothing was evaluable. */
  worstQualityLevel: PrintQualityLevel | null;
}
```

All additions are additive; no existing client code breaks.

### Service wiring (`DesignsService`)

- Warnings are computed **at read time**, never persisted. Asset dims are immutable
  after upload but print area physical specs can change; read-time compute is always
  current and avoids a stale snapshot in `designJson`.
- `toDto(...)` (used by create/update/findById): one extra
  `uploadedAsset.findMany({ where: { id: { in: assetIds } }, select: { id, width, height } })`
  for the design's assets, then `collectQualityWarnings(...)`. `toDto` becomes async.
- `toListItemDto(...)`: asset dims are batched **once per page** (collect every asset
  id across the page's rows, single `findMany`, pass the shared map down). No N+1.
  A row with an unreadable document keeps its existing degrade behavior and gets
  `worstQualityLevel: null`.
- `create`/`update`/`render` behavior is otherwise unchanged: **a poor design still
  saves and still renders.** No new error paths.

### Upload hardening (small in-scope fix)

`AssetsService.validateAndStore` reads `metadata.width/height` **before**
`.rotate()` re-encodes. For EXIF orientations 5 through 8 the stored file has swapped
dimensions versus the recorded ones, which would skew the DPI math. Fix: derive the
stored dims from the **encoded** buffer (`sharp(encoded).metadata()`, or swap when
`metadata.orientation >= 5`). One extra metadata read per upload, negligible cost.

### Endpoints

No new endpoints. No changes to `CreateDesignDto`. Warnings ride on the existing
design and list responses. No filesystem paths involved anywhere in the new fields.

## 6. Editor UX (`editor-client.tsx`)

The editor computes quality locally (same shared function) so feedback is live while
dragging the scale handles, with zero extra requests:

- Asset pixel size: `FabricImage.width/height` is the natural (source) size for both
  fresh uploads and re-opened designs, and the stored file is a same-size re-encode,
  so no API change is needed for the editor to know source dims.
- Per-area ppi: `printAreaPpi(area)` from the new `PrintAreaDto` fields.

### Warning badge on the selected object

The Position readout (step 02) gains a quality line, recomputed by `readSelection`
(already called on select and on `object:modified`):

```
center 500, 470    size 182 x 182    angle 0deg
print quality ~48 DPI · too low for sharp print        ← level-colored chip
```

- `data-testid="dpi-readout"`, `data-level="ok|warning|poor"` for tests.
- ok → muted "~238 DPI, good to print"; warning → amber "may look soft";
  poor → red "too low for sharp print". Copy follows the global rules (no dashes,
  no filler).
- Unknown (missing natural size) → line hidden entirely.

### Message before save when quality is poor

`handleSave` pre-flight (after geometry validation, before the request): collect
quality for every object across every area. If any are `poor`, the save **proceeds**
but the resulting status message carries a details list:

```
Design saved. Generate the mockups when ready.
• Front print, object 1: ~48 DPI, will likely print blurry
```

Advisory, deterministic, and testable; no confirm dialog (a modal would block the
Playwright flow and adds friction the POC does not need). Render stays gated only by
the existing saved+clean rule; the server-computed warnings then appear on the
preview page.

## 7. Preview and library UX

### `/designs/[id]` (preview page)

Renders `design.qualityWarnings` under the existing `kv` block when non-empty:

```
Print quality
  Front print, object 1: ~48 DPI, will likely print blurry
  Back print, object 2: ~119 DPI, may look soft up close
```

`data-testid="quality-warnings"`. Nothing shown when the list is empty.

### `/designs` (library)

Card gets a small level badge when `worstQualityLevel` is `warning` or `poor`
(`data-testid="quality-badge"`, e.g. "low res artwork"). `ok` and `null` show
nothing; the library stays calm by default.

## 8. Backend validation policy

- **Nothing blocks.** `validateDesignPlacements` is untouched; save and render accept
  poor-quality designs exactly as before.
- The server is still the authority for what the preview page and library display:
  warnings in API responses are always recomputed server-side from DB values, never
  echoed from the client.
- A future slice can add `?strict=` blocking or per-product thresholds; the constants
  and pure functions are already shared, so that becomes a policy change, not a math
  change.

## 11. Risks

1. **Canvas px vs physical inches is an assumption chain.** If the seeded inches are
   wrong, every DPI number is wrong. Mitigations: per-area columns make the spec
   explicit and editable; the 12 in fallback is documented in one constant; warnings
   are advisory so a wrong number annoys, never blocks.
2. **False positives on flat-color art.** A 400 px solid-shape logo can upscale
   acceptably in DTG. Copy says "may print blurry", never "cannot print"; nothing is
   blocked. Per-product thresholds are a future slice.
3. **False negatives for legacy assets without dims.** Unknown inputs are silent by
   design (no warning beats a wrong warning). New uploads always have dims.
4. **EXIF orientation dimension swap** (5 through 8) would invert dpiX/dpiY. Fixed in
   this slice (section 5); without the fix portrait phone photos would mis-rate.
5. **Physical aspect vs canvas rect aspect mismatch** (template author error) makes
   per-axis ppi diverge. min() keeps the verdict conservative; shared tests cover it.
6. **Future per-product print specs.** Different garments will have different
   platens. Columns on `PrintArea` are the right granularity today and migrate
   cleanly to a variant-level override later because the math only consumes resolved
   ppi values.
7. **`toDto` goes async + one extra query per design fetch.** Negligible at POC scale;
   the library path is batched to one query per page, so no N+1 regression.
8. **Scope creep magnets**: upload-time rejection, text-object quality, confirm
   modals, per-product thresholds, vector/SVG support. All out of scope.

## Implementation results (2026-06-06)

### Deviations from the plan

1. **`PrintQualityLevel` lives in `types.ts`**, not `quality.ts` (quality imports it).
   Avoids an `export *` name collision in the package index; the public API is
   unchanged because the index re-exports both modules.
2. **EXIF fix is a swap, not a re-read.** Stored dimensions are swapped when
   `metadata.orientation >= 5` instead of re-running `sharp().metadata()` on the
   encoded buffer. Same result, no second decode. Covered by an e2e test that
   uploads an orientation-6 JPEG and checks both the DB record and the streamed
   file's real pixels (50x100 from a 100x50 source).
3. **Worked-example DPI for the hi-res case is ~238 via the Y axis**, not X: the
   seeded front area's Y scale (340px / 15.7in ~ 21.66 px/in) is marginally below
   X (260/12 ~ 21.67), so min() picks Y. The plan's table said ~238 either way;
   the shared test pins the exact axis.
4. **e2e warning-band sizes**: the API tests use a full-area object (260x340) with
   2000px (127 DPI, warning) and 2400px (153 DPI, ok) assets instead of the
   table's 182px placement, keeping expected integers stable.

### Final behavior

- **Formula** exactly as planned (section 2); constants `DPI_OK_THRESHOLD = 150`,
  `DPI_POOR_THRESHOLD = 100`, `ASSUMED_PRINT_AREA_WIDTH_INCHES = 12` in
  `packages/shared/src/quality.ts`. Unknown inputs (missing asset dims, unusable
  geometry, unknown area) produce no warning anywhere.
- **Migration** `20260606160127_add_print_area_physical_size`: additive nullable
  `width_inches`/`height_inches` on `print_areas`; seed sets front 12 x 15.7,
  back 12 x 17.5.
- **API**: `PrintAreaDto.widthInches/heightInches`; `DesignProjectDto.qualityWarnings`
  (recomputed at read time, one batched asset query); `DesignListItemDto.worstQualityLevel`
  (one batched asset query per page, null for corrupt rows). Save and render accept
  poor designs unchanged. No new endpoints, no paths in any new field.
- **Editor**: live DPI chip under the Position readout (`data-testid="dpi-readout"`,
  `data-level`), computed locally from the FabricImage natural size and the area's
  ppi; save proceeds and lists poor objects in the status details.
- **Preview page**: "Print quality" block from the server's `qualityWarnings`.
- **Library**: per-card badge ("low res artwork" / "may print soft") when
  `worstQualityLevel` is poor/warning; nothing shown for ok/null.

### Limitations

- Physical sizes are template seed data; real garment specs may differ. Numbers are
  advisory and the columns are editable per area.
- Flat-color art can print acceptably below the thresholds; the copy says "may"
  and "likely", and nothing is ever blocked.
- Legacy assets without stored dimensions are silently skipped (no warning rather
  than a wrong one). All new uploads have dimensions.
- The editor evaluates quality with the shared math locally; its numbers can differ
  from the server's only if template physical specs change mid-session (refresh
  picks up the new values).
