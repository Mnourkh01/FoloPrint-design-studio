# v1.2 — Multi print areas (front + back)

Branch: `feature/v1.2-multi-print-areas` (from `staging`). Status: IMPLEMENTED; see
"Implementation notes" at the end for the small deltas from this plan.

## Goal

One sentence: a design can hold artwork on more than one print area of the same template
(front and back of the tee), with an area switcher in the editor and one rendered mockup
per printed area.

## Current state (v1.1)

- `PrintArea` table already supports N areas per template (`@@unique([productTemplateId, key])`),
  but the seed creates only `front` and every layer above assumes exactly one area:
  - `DesignDocument` v1: single `printAreaKey` + flat `objects[]`
  - `CreateDesignDto`: single `printAreaKey`
  - `DesignsService.validateAndBuildDocument` / `render`: one area, one preview
  - `DesignProject.previewPath`: single path, `previews/{id}.png`
  - Editor: `template.printAreas[0]` hardcoded, one boundary rect, one background
- The renderer (`renderMockup`) is already per-area by signature (one `printArea`, one base,
  one overlay). It needs no internal change; it just gets called once per area.

## Key decisions

### D1. Front and back are different physical views

A back print cannot appear on the front photo. Each print area therefore carries its own
base/overlay images, nullable with fallback to the template's images:

```prisma
model PrintArea {
  // ... existing fields ...
  baseImagePath    String?   // null -> fall back to template.baseImagePath
  overlayImagePath String?   // null -> fall back to template.overlayImagePath
}
```

Rejected alternative: a separate `TemplateView` model (view -> N areas, Printful-style).
Correct for a real catalog, over-engineered for this POC where 1 view = 1 area. The nullable
columns migrate cleanly into a View model later if needed.

### D2. Design document v2 with placements

```ts
interface DesignPlacement {
  printAreaKey: string;
  objects: DesignObject[];   // unchanged shape
}

interface DesignDocument {
  version: 2;
  templateId: string;
  placements: DesignPlacement[];  // min 1, unique printAreaKey, each placement min 1 object
}
```

A placement exists only if it has at least one object. No empty placements stored.

### D3. v1 documents: read-time normalization, no data migration

Shared package gains `normalizeDesignDocument(raw): DesignDocument` that maps
`{version: 1, printAreaKey, objects}` to `{version: 2, placements: [{printAreaKey, objects}]}`
and passes v2 through. Every read path (service `toDto`, `render`) normalizes first.
Documents are rewritten as v2 naturally on the next update. No SQL touches `designJson`.

### D4. One preview file per area, rendered together

- `POST /designs/:id/render` renders every placement in the document (sequentially) and
  returns all previews. No per-area render param in v1.2; a design has at most a few areas
  and partial renders complicate staleness tracking.
- Storage layout: `previews/{designId}/{areaKey}.png` (deterministic, via `StorageService`).
- Streaming: `GET /designs/:id/preview/:areaKey`. The old `GET /designs/:id/preview` is
  removed; the web app is the only consumer.
- DB: `DesignProject.previewPath String?` is replaced by `previewPaths Json?`
  (map `areaKey -> relative path`). Existing previews are stale POC artifacts: the migration
  drops the column; previews re-render on demand. Reversible (re-add column, null values).

### D5. Editor: one Fabric canvas, visibility toggle per area

Tabs above the stage (Front / Back). All design objects stay on the one canvas, each tagged
with `printAreaKey`; switching tabs:

- swaps `canvas.backgroundImage` / `overlayImage` to the area's images (with template fallback),
- swaps the boundary rect to the active area,
- sets `visible` + `evented` = (object.printAreaKey === activeKey), clears selection.

Rejected alternative: serialize objects out and rebuild the canvas per switch. Re-instantiates
FabricImages (flicker, async churn) for no benefit.

Clamp/fit logic keys off the active area. Save collects all areas into `placements`
(areas with zero objects omitted). Per-tab object count badge. Dirty flag stays global.

## API contract changes

### DTO (breaking, POC-acceptable)

```ts
class DesignPlacementDto {
  @IsString() @Length(1, 50)
  printAreaKey!: string;

  @IsArray() @ArrayMinSize(1) @ArrayMaxSize(20)
  @ValidateNested({ each: true }) @Type(() => DesignObjectDto)
  objects!: DesignObjectDto[];
}

class CreateDesignDto {
  @IsUUID()
  templateId!: string;

  @IsArray() @ArrayMinSize(1) @ArrayMaxSize(8)
  @ValidateNested({ each: true }) @Type(() => DesignPlacementDto)
  placements!: DesignPlacementDto[];
}
```

Service-level validation (per placement, error messages keep `placements[i].objects[j]` shape):
1. every `printAreaKey` exists and is active on the template
2. no duplicate `printAreaKey` in the payload
3. all referenced assets exist (single batched query across placements)
4. geometry: `validateDesignObjects(placement.objects, area)` per placement

### Response DTOs

- `PrintAreaDto` += `imageUrl: string | null`, `overlayUrl: string | null`
  (relative API URLs `/templates/:slug/areas/:key/image|overlay`, null when falling back —
  client then uses the template-level URLs). No filesystem paths, as before.
- `DesignProjectDto.previewUrl: string | null` becomes
  `previews: { printAreaKey: string; url: string }[]` (empty until rendered).
- `RenderResultDto` becomes `{ id, previews: { printAreaKey, url }[] }`.

### Endpoints

| Change | Endpoint |
|---|---|
| modify | `POST /designs`, `PUT /designs/:id` — body shape v2 |
| modify | `POST /designs/:id/render` — renders all placements |
| add | `GET /designs/:id/preview/:areaKey` |
| remove | `GET /designs/:id/preview` |
| add | `GET /templates/:slug/areas/:key/image` and `/overlay` (stream area images) |

## Renderer

No changes to `packages/renderer`. The service calls `renderMockup` once per placement with
that area's resolved base/overlay (fallback to template) and that area's rect.

## Seed

- Generate back-of-tee SVGs (body without the collar dip, plain back seam) ->
  `templates/classic-tee-back-base.png` / `-back-overlay.png`.
- Upsert `back` print area: own image paths, rect approx `x: 370, y: 260, width: 260, height: 380`
  (tune visually).
- `front` area keeps null image paths (falls back to template images). Exercises both code paths.

## Web

- `editor-client.tsx`: area tabs, per-area boundary + background/overlay swap, objects tagged
  with `printAreaKey`, save builds `placements`, validation errors mapped per area.
- Re-open mode: place each placement's objects with their area tag; activate the first
  placement's tab.
- `designs/[id]/page.tsx`: one preview image per rendered area, labeled with area name;
  render button triggers the all-areas render.
- `lib/api.ts`: updated types flow from `@foloprint/shared` (compile-time enforcement).

## Migration plan (Prisma)

One migration, reversible:

1. `print_areas`: add nullable `baseImagePath`, `overlayImagePath`.
2. `design_projects`: drop `previewPath`, add `previewPaths Json?`.

No data backfill. Stored v1 `designJson` untouched (D3). Old preview PNGs under `previews/`
become orphans; acceptable for POC (note in cleanup backlog).

- [ ] Editor switches areas; artwork stays per-area; clamping uses the active area
- [ ] Save validates every placement server-side; precise per-placement errors

## Out of scope for v1.2

Text objects, DPI warnings, render queue, per-area render endpoint, TemplateView model,
auth, storage drivers. Hard boundaries from PLAN.md unchanged.

## Implementation notes (delta from plan)

- `PrintArea.sortOrder Int @default(0)` added: key-asc ordering would put "back" before
  "front" in the editor tabs and preview list. Shipped as a second migration
  (`print_area_sort_order`) because the first one was already applied locally and Prisma
  checksums applied migration files.
- `RenderResultDto` is `{ designId, previews }` and each preview entry carries
  `renderedAt` (stored per area in the `previewPaths` JSON map), per review requirements.
- Preview metadata is ordered by area `sortOrder` (front before back), not key order.
- `previewPaths` JSON shape: `{ [printAreaKey]: { path, renderedAt } }`. Paths stay
  server-side; responses only carry `/designs/:id/preview/:printAreaKey` URLs.
- Editor serializes normalized fields only (assetId, center x/y, scaled width/height,
  rotation, printAreaKey), never raw Fabric JSON. Hidden inactive-area objects keep their
  geometry and save correctly; the Playwright suite proves a hidden back object that would
  violate the front area still saves (per-area validation).
