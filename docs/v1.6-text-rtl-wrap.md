# v1.6 — RTL/Arabic Text + Auto-Wrap

Status: **implemented** (all four suites green; spike results and implementation notes in §11)
Branch: `feature/v1.6-text-rtl-wrap` (from `staging` @ `f7949e0`)

Goal: finish the text story after v1.5. Users can write Arabic (RTL) text and turn on
controlled auto-wrap inside the text box, and both render identically in the Fabric editor
and the server-side sharp mockups. Explicit `\n` line breaks keep working exactly as in
v1.5, and every existing text design stays valid without migration.

Out of scope (explicitly): storage drivers, render queue, per-product print specs,
per-character styling, curved/path text, font uploads.

---

## 0. Spike first (same discipline as v1.5)

v1.5 proved sharp/Pango text works on Windows prebuilt libvips. v1.6 needs four more facts
proven before any contract code is written:

| # | Question | How to prove | Bail-out if it fails |
|---|---|---|---|
| S1 | Does Pango on the prebuilt Windows libvips shape Arabic correctly (contextual forms + ligatures) with a bundled Noto Naskh Arabic TTF via `fontfile`? | Render `مرحبا بالعالم`, compare raster width against the same letters separated by spaces (shaped joined forms are materially narrower) | Slice is dead on Windows dev; re-scope to wrap-only |
| S2 | Can we force base direction by prepending U+200E (LRM) / U+200F (RLM), given sharp exposes no Pango direction option? | Render a mixed line (`ABC مرحبا`) twice, once with LRM and once with RLM prepended; rasters must differ and word order must flip | Fall back to `direction: 'auto'` only (first-strong, Pango default) and drop the explicit selector |
| S3 | Does Noto Naskh Arabic contain Basic Latin glyphs (A–Z, digits, punctuation)? | Render `ABC 123 ?!` with only that fontfile; inspect for tofu/fallback | Editor warns when Latin chars are used with the Arabic font; renderer result may diverge, document it |
| S4 | Is Fabric v6 `direction: 'rtl'` + IText/Textbox editing usable (rendering correct, cursor not unusable)? | Manual browser check on a scratch page: type Arabic, select, move cursor, wrap | Keep rendering RTL but document editing quirks as POC limitation |

Verified facts already in hand (read from `node_modules`, not assumed):

- Fabric v6 `Text` has a `direction: CanvasDirection` property (sets `ctx.direction`).
- Fabric renders a whole uniform-styled line through **one** `fillText` call (the
  `timeToRender` shortcut fires only at line end when there is no `charSpacing`, no `path`,
  no per-char styles). We use none of those, so the **browser shapes Arabic natively** in
  display. But Fabric *measures* per grapheme (`__charBounds`) without shaping context, so
  measured widths for Arabic are wrong-ish. This asymmetry drives the wrap design in §3.
- sharp's `text` input supports `width` (px word-wrap) and `wrap: 'word' | 'char' |
  'word-char' | 'none'`. We will deliberately **not** use Pango wrapping (§3).

| Key | Family | File | License | Source |
|---|---|---|---|---|
| `noto-naskh-arabic` | Noto Naskh Arabic | `noto-naskh-arabic.ttf` | OFL 1.1 | google/fonts `ofl/notonaskharabic` |

- Same rules as v1.5: OFL verified at source, `OFL.txt` checked in next to the binary at
  `packages/renderer/fonts/noto-naskh-arabic/`, bracket-free filename (PowerShell
  `-OutFile` wildcard gotcha), variable TTF used at its default (Regular) weight.
- One new row in `FONT_WHITELIST` (`packages/shared/src/fonts.ts`). Nothing else changes:

  `resolveFont` are all already generic over the whitelist.
- Browser and server load the **same TTF**, so HarfBuzz shaping in Chrome and HarfBuzz

Why Noto Naskh Arabic and not Cairo/Tajawal/Amiri: Naskh is the default reading style for
product text, the Noto project has the broadest Arabic codepoint coverage, and it ships
Basic Latin in the same file (to be confirmed by S3), which avoids a second fallback font.

## 2. Contract changes — two optional fields + one derived field

```ts
export type TextDirection = 'ltr' | 'rtl' | 'auto';
export type TextWrapMode = 'none' | 'box';

export interface TextDesignObject extends DesignObjectBase {
  type: 'text';
  /** Raw user text. `\n` only for explicit breaks. Source of truth, user-editable. */
  text: string;
  fontFamily: string;
  fontSize: number;
  color: string;
  align: TextAlign;
  /** Base direction. 'auto' = first strong character decides. Default 'auto'. */
  direction?: TextDirection;
  /** 'box' = auto-wrap at the stored width (editor Textbox). Default 'none'. */
  wrapMode?: TextWrapMode;
  /**
   * Derived render cache, REQUIRED when wrapMode === 'box', FORBIDDEN otherwise.
   * The exact visual lines the editor produced at save time (soft wraps + explicit
   * breaks flattened, in order). The server renders these lines verbatim, so the
   * mockup breaks exactly where the editor broke. Regenerated on every save.
   */
  wrappedLines?: string[];
}
```

- **Document version stays v2.** Purely additive: a stored text object without
  `direction` normalizes to `'auto'`, without `wrapMode` to `'none'`
  (`normalizeDesignObject` gains two defaults). Every v1.5 text design is already valid.
  Same reasoning as the v1.5 no-v3 decision: old readers ignore the new fields and still
  render correctly.
- For `wrapMode: 'box'`, the existing stored `width` **is** the wrap box width (Fabric
  Textbox semantics: side handles set width, text reflows). No separate `wrapWidth` field.
- No new fields on image objects; kind purity (§5) extends to reject them there.

### Why store derived lines instead of letting both sides wrap raw text

The alternative (store raw text + let Pango wrap at `width`) was rejected:

- Fabric computes wrap points from **unshaped per-grapheme measurements**; Pango computes
  them from **shaped runs**. For Arabic these word widths genuinely differ, and a word near
  the box edge breaks differently per side.
- A different break point changes the **line count**, and through render-then-fit a
  different line count becomes a visible vertical stretch of every glyph. That is the worst
  drift artifact this project can produce, and no tolerance tuning fixes it.
- Storing the editor's lines makes break parity **exact by construction**, and it is
  server-verifiable (§5: strip-whitespace reconciliation against raw `text`), so the
  derived field cannot be forged into rendering text that was never validated.

Reopen behavior: the editor restores the Textbox from raw `text` + stored `width` and
re-wraps live with its own engine (self-consistent), then regenerates `wrappedLines` on
the next save. `wrappedLines` is never edited, only derived.

## 3. Direction plan

### Shared resolver (single source of truth)

New pure helper in `packages/shared/src/text.ts`:

```ts
/** First-strong-character scan. Arabic blocks => 'rtl', else 'ltr' on first strong LTR
 *  char; all-neutral text defaults 'ltr'. Explicit direction short-circuits. */
export function resolveTextDirection(text: string, direction: TextDirection = 'auto'): 'ltr' | 'rtl';
```

Strong-RTL detection ranges: U+0590–U+08FF (Hebrew, Arabic, Syriac, Arabic Supplement +
Extended-A), U+FB50–U+FDFF and U+FE70–U+FEFF (presentation forms). Dependency-free, ~15
lines, exhaustively unit-tested. Both editor and renderer call this one function, so
"auto" can never resolve differently on the two sides.

### Editor (Fabric)

- Set the Fabric object's `direction` to the resolved value ('ltr' | 'rtl'); re-resolve on
  every text change while the selector sits on Auto.
- Display shaping is already correct via the uniform-style whole-line `fillText` shortcut.
- Cursor/selection in RTL has known upstream quirks (S4 scopes how bad); accepted as POC
  limitation, documented in the implementation results.

### Renderer (Pango via sharp)

sharp exposes no base-direction option, so the renderer forces it with directional marks:
prepend U+200F (RLM) for resolved 'rtl' or U+200E (LRM) for resolved 'ltr' to **each
paragraph** (each `\n`-separated segment) at render time. Pango picks base direction per
paragraph from the first strong character; the mark is that character and is zero-width.

- Marks are injected **only at render time**, never stored, so document content stays
  exactly what the user typed. Stored-text validation (§5) keeps rejecting all C0 control
  chars and additionally rejects stored bidi-control characters so a crafted payload
  cannot smuggle its own direction overrides.
- This stays inside Pango's plain-text path. No markup, no SVG, color still applied via
  the dest-in flat-color composite. The v1.5 injection-safety posture is unchanged.

### Alignment under RTL

Pango interprets left/right alignment relative to the resolved paragraph direction (it can
flip them); canvas `textAlign` does not. A renderer test pins the actual behavior with the
shipped libvips, and if Pango flips, the renderer maps `align` (swap left/right) for
resolved-RTL text so the contract's `align` always means visual left/right. Decided by
test, not assumption.

## 4. Auto-wrap plan

- **Editor**: `wrapMode: 'box'` uses Fabric `Textbox` instead of `IText` (same family,
  same props). Side middle handles are enabled *only* on Textbox (v1.5 keeps them off for
  IText) because in Textbox they change the wrap width without scaling glyphs, which is
  exactly the controlled behavior we want. Corner handles still scale uniformly, and the
  v1.5 save-time bake extends to Textbox: `fontSize *= scale` and `width *= scale`, then
  scale resets to 1. `clampTextScale` applies unchanged.
- **Wrap calculation**: the editor is the only wrap engine (Fabric Textbox word-wrap,
  breaking on whitespace; long unbreakable words overflow the box width rather than break
  mid-word, matching Textbox defaults). At save, the editor reads Textbox's computed text
  lines and stores them as `wrappedLines`.
- **Server**: joins `wrappedLines` with `\n`, prepends direction marks per line, renders
  with Pango `wrap: 'none'` (no `width`), then runs the existing render-then-fit into the
  stored box. The renderer never re-wraps, so there is **no wrap engine mismatch by
  construction**. Renderer changes are minimal: the v1.5 multi-line path already handles
  `\n`.
- **Stored text**: raw `text` keeps only explicit `\n` (CRLF still normalized at input).
  Soft wraps live only in `wrappedLines`. Toggling wrap off discards `wrappedLines` and
  the raw text simply renders with its explicit breaks — no data loss either direction.
- **Max lines / overflow**: `TEXT_MAX_LINES` (8) now applies to the **visual line count**:
  raw-text explicit breaks for `wrapMode: 'none'` (unchanged), `wrappedLines.length` for
  `'box'`. When live wrapping exceeds 8 lines or the wrapped block's height overflows the
  print area, the editor shows a clear inline warning and blocks save (the server would
  reject it anyway; the warning just says why before the round-trip). `TEXT_MAX_LENGTH`
  (300) stays on raw text.

## 5. Validation (server authority, shared rules)

`packages/shared/src/text.ts` additions, consumed by both editor (UX) and API (authority):

| Rule | Detail |
|---|---|
| `direction` | must be `'ltr' \| 'rtl' \| 'auto'` when present |
| `wrapMode` | must be `'none' \| 'box'` when present |
| `wrappedLines` presence | required (non-empty array) iff `wrapMode === 'box'`; forbidden otherwise |
| `wrappedLines` content | every entry a string passing the existing control-char rule, no `\n` inside an entry; `length <= TEXT_MAX_LINES` |
| Reconciliation | `wrappedLines` joined and stripped of all whitespace must equal raw `text` stripped of all whitespace; otherwise the cache is forged/stale → reject |
| Bidi controls | stored `text` and `wrappedLines` reject U+200E, U+200F, U+202A–U+202E, U+2066–U+2069 (direction is contract data, not embedded characters) |
| Kind purity | image objects must not carry `direction` / `wrapMode` / `wrappedLines` (same `!== undefined` comparison as v1.5 — `useDefineForClassFields` gotcha) |
| Unchanged | 300-char cap, 8-line cap on explicit breaks, font whitelist, 12–500 size, `#RRGGBB`, align enum, geometry bounds per print area |

DTO (`apps/api/.../create-design.dto.ts`): extend the single `DesignObjectDto` with the
three optional fields under the same `@ValidateIf` type-gating pattern v1.5 chose over a
class-transformer discriminator (`whitelist + forbidNonWhitelisted` stays on).

## 6. Renderer plan

`RenderTextObject` gains `direction: 'ltr' | 'rtl'` (already resolved by the service via
the shared resolver — the renderer never guesses) and `lines: string[]` (the final visual
lines: `wrappedLines` for box mode, `text.split('\n')` otherwise — service maps it).

`prepareTextLayer` changes, in order:

1. Build the Pango input: for each line, prepend the direction mark, join with `\n`.
2. Render via the existing plain-text sharp `text` input — same `fontfile`, `dpi: 72`,
   `align` (possibly swapped for RTL per the §3 pinned test), `wrap` not used.
3. Existing pipeline unchanged: dest-in flat-color tint → render-then-fit resize into the
   stored box → shared rotate/position path.

No new sharp features, no markup, no SVG. The only genuinely new renderer surface is the
direction mark and the Arabic font binary.

## 7. Editor UX plan

Text panel (existing right-side panel from v1.5) gains, top to bottom:

- **Font select**: + "Noto Naskh Arabic" option (renders in its own face like the others).
- **Direction**: 3-state segmented control `Auto · LTR · RTL`, default Auto. While on
  Auto, the control hints the resolved direction (e.g. the active glyph highlights) so the
  user sees what Auto decided. Maps to the Fabric `direction` prop + contract field.
- **Wrap toggle**: "Wrap in box" switch. On = swap IText → Textbox (preserving text,
  font, size, color, align, direction, center position) with an initial width of the
  current measured width; off = swap back, soft wraps dissolve. Swap preserves selection.
- **Overflow warning**: inline, non-dismissable while true: "Text wraps to more than 8
  lines" or "Text overflows the print area" with save blocked and the reason shown at the
  button. Mirrors the server rule, so users never hit a surprise 400.
- Arabic typing works in both IText and Textbox; cursor quirks (if S4 finds them) get a
  one-line note in the panel only if genuinely confusing, otherwise just documented.

### Alignment pin (decided by test, as planned)

Pango **flips** left/right for RTL paragraphs (`align: left` puts the short line at the
**right** edge = line-start). The renderer therefore swaps left↔right for resolved-RTL
text (`PANGO_ALIGN_RTL`), so the contract's `align` always means visual left/right.
Pinned by the renderer test "align is visual for RTL".

### Bug found and fixed during browser verification

Fabric's default `strokeWidth` (1) inflates `getScaledWidth()` by 1px even with no
stroke. Saved wrap width was therefore wrap-width+1, and a reopened Textbox got a
1px-wider box, which flipped a boundary-tight line break (3 lines → 2). Text objects
now set `strokeWidth: 0`; round-trip wrap is exact (pinned by the Playwright reopen
assertions).

### Known limitations (accepted for POC)

- RTL cursor movement in Fabric is logical-order (arrow keys move by string index,
  which visually reverses in RTL text). Standard canvas-editor quirk; rendering and
  the saved document are unaffected.
- Fabric measures Arabic per unshaped grapheme, so the selection box can sit a few
  px off the shaped glyphs. Render-then-fit absorbs it server-side.
- Reopen re-wraps live from raw text + stored width (per design). Breaks regenerate
  identically now that widths round-trip exactly, but `wrappedLines` only ever
  reflects the last save.
- Mixed-bidi punctuation inside one line can place differently between browser and
  Pango in extreme cases; same HarfBuzz + same TTF bounds it, not observed in tests.
